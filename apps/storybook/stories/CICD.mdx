# CI/CD Pipelines

Wakecore uses 5 GitHub Actions workflows that work together to validate code, run visual regression tests, and publish packages across two release channels.

## Quality Gate

**File:** `.github/workflows/ci.yml`

The core CI pipeline. Every push and PR to `main` or `develop` must pass this gate before anything can be published. It runs **4 parallel jobs:**

<table>
	<thead>
		<tr>
			<th>Job</th>
			<th>Runs On</th>
			<th>What It Does</th>
		</tr>
	</thead>
	<tbody>
		<tr>
			<td>
				<strong>Commit Messages</strong>
			</td>
			<td>PRs only</td>
			<td>
				Validates commit messages against <a href="https://www.conventionalcommits.org/">Conventional Commits</a> via
				commitlint
			</td>
		</tr>
		<tr>
			<td>
				<strong>Lint &amp; Format</strong>
			</td>
			<td>Always</td>
			<td>Runs Oxlint and Oxfmt format check across all packages</td>
		</tr>
		<tr>
			<td>
				<strong>Build &amp; Typecheck</strong>
			</td>
			<td>Always</td>
			<td>
				Builds all <code>@wakecap/core-*</code> packages, runs typecheck (tsgo), builds the web app
			</td>
		</tr>
		<tr>
			<td>
				<strong>Test</strong>
			</td>
			<td>Always</td>
			<td>

				browser mode

**Downstream:** Both publish workflows wait for Quality Gate to succeed before running. Nothing gets published from broken code.

## Chromatic

**File:** `.github/workflows/chromatic.yml`

Visual regression testing for Storybook. Builds Storybook, uploads snapshots to Chromatic, and compares against baselines.

**Triggers:**

- **Push to main/develop** — auto-accepts visual changes (baselines update after merge)
- **PR to main/develop** — visual diffs must be reviewed and approved before merging

**Key settings:**

- `exitZeroOnChanges: false` — visual diffs **block** the PR until reviewed
- `onlyChanged: true` — only snapshots stories that changed (faster builds)
- `autoAcceptChanges: "{main,develop}"` — auto-accepts on branch pushes (safe because PRs already reviewed the changes)

**Required secrets:**

- `CHROMATIC_PROJECT_TOKEN` — Chromatic project authentication
- `VITE_MAPBOX_TOKEN` — needed for map stories to render correctly (validated before build)

## Publish Packages (stable)

**File:** `.github/workflows/publish.yml`

Manages stable releases to GitHub Packages using [Changesets](https://github.com/changesets/changesets).

**Trigger:** Runs on every push to `main` (i.e., merged PRs). Also supports manual trigger via `workflow_dispatch`. Safe because branch protection ensures all PRs pass Quality Gate before merging.

**How it works:**

1. `changesets/action` checks for `.changeset/*.md` files
2. **If changesets exist** → opens/updates a "Version Packages" PR that bumps `package.json` versions, generates changelogs, and deletes consumed changeset files
3. **If no changesets exist** (version bump PR was just merged) → publishes packages to GitHub Packages with the `@latest` tag

**How to trigger a version bump:**

```bash
# 1. Create a changeset describing your change
pnpm changeset

# 2. Select affected packages and bump type (patch/minor/major)
# 3. Commit the generated .changeset/*.md file with your PR
# 4. After PR merges to develop, then develop merges to main,
#    Changesets opens a "Version Packages" PR automatically
# 5. Merging that PR publishes to GitHub Packages
```

## Publish Pre-release (next)

**File:** `.github/workflows/publish-next.yml`

Publishes pre-release packages on every successful merge to `develop`.

**Trigger:** Runs on every push to `develop` (i.e., merged PRs). Safe because branch protection ensures all PRs pass Quality Gate before merging.

**Version format:**

```
{package-version}-next.{YYYYMMDD}.{HHMMSS}.{short-sha}
```

Each package uses its own `package.json` version as the base, so versions stay accurate even if packages are at different stable versions.

**Example versions:**

```
@wakecap/core-tokens@0.1.0-next.20260416.143022.abc1234
@wakecap/core-utils@0.0.1-next.20260416.143022.abc1234
@wakecap/core-ui@0.2.0-next.20260416.143022.abc1234
```

**Install pre-release packages:**

```bash
pnpm add @wakecap/core-ui@next @wakecap/core-tokens@next @wakecap/core-utils@next
```

**Publish order:** tokens → utils → components (respects the dependency chain).

## Intent — Validate Skills

**File:** `.github/workflows/intent-validate.yml`

Validates TanStack Intent SKILL.md files whenever skill content changes.

**Trigger:** Push or PR to main/develop, only when files in `packages/*/skills/**` or `skills/_artifacts/**` change.

**How it works:** Runs `pnpm exec intent validate` for each package in parallel via a matrix strategy:

- `packages/components` — 5 skills (core-ui-components, core-ui-forms, core-ui-data-table, core-ui-charts, core-ui-chat)
- `packages/tokens` — 2 skills (core-tokens, core-ui-quickstart)
- `packages/utils` — 1 skill (core-utils)

See the [Agent Skills](?path=/docs/agent-skills--docs) page for details on what skills are and how they work.

## Pipeline Diagram

How the workflows connect for a typical feature development cycle:

```
Feature PR → develop
  ├── Quality Gate (4 parallel jobs)
  │     ├── Commit Messages (PR only)
  │     ├── Lint & Format
  │     ├── Build & Typecheck
  │     └── Test (441 browser tests)
  ├── Chromatic (visual regression review)
  └── Intent Validate (if skills changed)

PR merges → push to develop
  ├── Quality Gate runs again
  ├── Publish Pre-release (@next)
  ├── Chromatic (auto-accept baselines)
  └── Intent Validate (if skills changed)

Periodic: develop → PR to main → merge
  ├── Quality Gate runs
  ├── Publish Packages (Changesets)
  ├── Chromatic (auto-accept baselines)
  └── Intent Validate (if skills changed)
```

## Running Locally

All CI checks can be run locally before pushing:

```bash
# Lint & Format
pnpm lint
pnpm format:check

# Build & Typecheck
pnpm --filter "@wakecap/core-*" build
pnpm typecheck

# Tests (requires Playwright)
pnpm test

# Validate Intent skills
pnpm exec intent validate packages/components/skills
pnpm exec intent validate packages/tokens/skills
pnpm exec intent validate packages/utils/skills

# Build Storybook
VITE_MAPBOX_TOKEN=your_token pnpm --filter apps-storybook build
```
