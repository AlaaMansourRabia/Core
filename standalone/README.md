# standalone

Builds a template into **one self-contained `.html` file** you can email, drop in Slack, or put on a
share. The recipient double-clicks it. No clone, no install, no server, no network.

```bash
node standalone/build.mjs
```

Output lands in `standalone/dist/`:

| File                         | Template                                                     |
| ---------------------------- | ------------------------------------------------------------ |
| `wakecap-app-installer.html` | `AppInstaller` — `@wakecap/core-ui/pages/core-app-installer` |
| `wakecap-workforce.html`     | `Workforce` — `@wakecap/core-ui/pages/core-workforce`        |

## What "self-contained" means here

Everything is inlined: the JS bundle, all CSS, and the Figtree / IBM Plex Mono webfonts as base64.
Verified in a headless browser with the network **switched off**, loaded over `file://` — zero external
requests, zero console errors, and the surfaces stay interactive (tabs, filters, tables, settings).

## The Storybook toolbar button (dev only)

Storybook's **Export HTML** tool (`apps/storybook/.storybook/html-export/`) exports the selected
story through this same builder. It POSTs to `/__wakecore/export-html`, which is **Vite dev-server
middleware** — every click runs a real Vite build over the story source.

A built Storybook is static files, so that endpoint does not exist on core.wakecap.com: the request
comes back `405` and the button is deliberately disabled there, labelled _Export HTML (local only)_.
Run `pnpm storybook` to export. Making it work on the hosted Storybook would mean either
pre-generating the HTML for every story at build time (798 stories, one Vite build each) or standing
up a build service behind the endpoint — neither is a static-host change.

## Prerequisites

`@wakecap/core-ui` must be built first, since the entries import from its `dist`:

```bash
pnpm --filter @wakecap/core-ui build
```

## Adding a template

Add an entry to `TARGETS` in `build.mjs`, then create the matching `<name>.html` and
`src/<name>.tsx` next to the existing pair.

## Exporting any Storybook story

Run Storybook and select any canvas story under Templates, Widgets, or Components. Use the
**Export HTML** action in the canvas toolbar. Storybook builds and downloads that exact story as one
self-contained `.html` file.

```bash
pnpm storybook
```

The same exporter is available from the command line after Storybook has been built (the static
build provides the authoritative story IDs in `apps/storybook/dist/index.json`):

```bash
pnpm export:html -- --story templates-appinstaller--default
pnpm export:html -- --story widgets-data-datatable--default
pnpm export:html -- --story components-primitives-button--default
```

Use `--theme dark` to export the dark Storybook global. `--out <directory>` changes the output
directory; it defaults to `standalone/dist/`.

The downloaded file keeps React as an internal implementation detail. JavaScript, WakeCore CSS,
fonts, imported assets, and referenced files from `apps/storybook/public/` are folded into the HTML,
so the recipient can double-click it without installing dependencies or starting a server.

## Notes

- `standalone/` is deliberately **not** a pnpm workspace package. It resolves vite, React and the
  React plugin through `apps/storybook`, which already has them, so it needs no install of its own.
- Fonts are regenerated by `node standalone/build-fonts.mjs` (the only step that touches the
  network). Re-run it only when the font stack in `packages/tokens/src/fonts.css` changes.
- Workforce's **Map View** tab shows its placeholder. That tab takes a `mapStage` — a 3D/map engine
  the host app mounts — which a static file cannot supply.
- Both files use `localStorage`, so a viewer's tab/project selection survives a reload. Two
  different templates opened from the same folder share the `file://` origin and therefore the same
  storage keys; that is also true of the templates inside Storybook.
